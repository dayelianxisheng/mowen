## 1. 真机整体架构

```
cmd_vel ──→ newt.py(串口) ──→ MCU ──→ 4个电机(PID控制)
                                     ↓
              pubv.py(串口读取) → /vel_raw → base_node → /odom_raw ──→ robot_localization EKF ← /wit/imu
                                                                              ↓                   ← rf2o激光里程计
                                                                            /odom → AMCL(omni) + move_base(DWA holonomic)
```

### 核心设计思想

- **MCU 包揽运动学**：ROS 只发 `cmd_vel` (vx, vy, vtheta)，MCU 自己算 4 个轮子转速并 PID 控制电机。ROS 端没有任何 mecanum 逆运动学代码。
- **MCU 回传速度**：`pubv.py` 从串口读取 MCU 发回的实测速度，生成里程计。
- **双重协议共存**：`newt.py` 发全向指令 (vx+vy+vtheta)，`teleop_send_vel_mowen.py` 发差速指令 (vx+vtheta only)。不同固件版本。
- **多源融合**：EKF 融合轮式里程计 + IMU + 激光里程计，任一源失效都能维持定位。

## 4. 串口协议（迁移 ros2_control 的蓝本）

### 下发协议（newt.py → MCU）：9 字节

```
Byte 0-1: 0xAA 0xBB          (帧头)
Byte 2:   0x0A               (命令类型)
Byte 3:   0x12               (子命令)
Byte 4:   0x02               (数据长度)
Byte 5-6: vx (低字节, 高字节)  signed 16-bit, 值 = cmd_vel.linear.x * 1000
Byte 7-8: vy (低字节, 高字节)  signed 16-bit, 值 = cmd_vel.linear.y * 1000
Byte 9-10: vθ (低字节, 高字节) signed 16-bit, 值 = cmd_vel.angular.z * 1000
Byte 11:  0x00               (结束/校验)
```

### 回传协议（MCU → pubv.py）：12 字节

```
Byte 0-1:  0xAA 0xBB          (帧头)
Byte 2-3:  a1, a2             (设备状态)
Byte 4-5:  vx (低字节, 高字节)  signed 16-bit, /1000 = m/s
Byte 6-7:  vy (低字节, 高字节)  signed 16-bit, /1000 = m/s
Byte 8-9:  vθ (低字节, 高字节)  signed 16-bit, /1000 * 0.75 = rad/s
Byte 10:   tzw?               (保留)
Byte 11:   checksum           = (a1+a2+vx_l+vx_h+vy_l+vy_h+vθ_l+vθ_h) & 0xFF
```

### 硬件接口

- 芯片：CH340 USB-TTL (`1a86:7523`)
- UDEV 规则：`/dev/carserial`（CH340）、`/dev/imu`（WIT IMU）、`/dev/lslidar`（镭神雷达）
- 波特率：115200

## 5. 导航启动链路对比

### 真机（nav777.launch）

```
map_server → 激光驱动 → 机器人模型 → IMU → pubv.py(读MCU) → base_node(/odom_raw)
→ robot_localization EKF(/odom) → AMCL(omni) → move_base(DWA holonomic) → newt.py → MCU
```

### 仿真（navigation.launch.py）

```
map_server → AMCL(OmniMotionModel) → planner_server(Navfn) → controller_server(DWB)
→ velocity_smoother → cmd_vel_nav → Gazebo planar_move → 模型整体移动
```

### 真机有仿真缺的

| 组件 | 作用 | 仿真是否需要 |
|------|------|------------|
| robot_localization EKF | 融合轮式里程计+IMU+激光里程计 | 不需要，仿真里程计完美 |
| rf2o 激光里程计 | 备选里程计源 | 不需要 |
| MCU 串口通信 | 下发 cmd_vel、回传速度 | 不需要 |
| IMU | 姿态估计 | 不需要（仿真用 gazebo 物理） |

## 6. Bug 13 重新评估：轮子不转

### 真机为什么轮子转

MCU 收到 `cmd_vel` → MCU 自己算 mecanum 逆运动学 → 4 路 PWM 驱动电机 → 轮子物理转动 → 编码器回传。

### 仿真为什么轮子不转

`planar_move` 直接 `SetLinearVel()/SetAngularVel()` 移动整个模型，绕过关节。轮子关节 angle 永远是 0。

### 推荐方案（同时解决仿真+真机迁移）

```
            ┌─ 仿真 ───────────────────────────────────────────┐
            │  gazebo_ros_control → Gazebo 关节(SetVelocity)   │
cmd_vel → MecanumDriveController ┤                             ├→ 轮子物理转动
            │  serial_hardware_interface → MCU → 4电机(PWM)    │
            └─ 真机 ───────────────────────────────────────────┘
```

- 仿真和真机共用同一个 `MecanumDriveController`
- 只切换底层 hardware interface（gazebo ↔ serial）
- 轮子不转 Bug 自然消失
- 真机的 `newt.py` 协议 → 重写为 `serial_hardware_interface`
